
# Genesis Invention Proposals

## Purpose

This directory stores invention proposals generated by Revela Genesis Core-One.

Genesis accepts demands, applies Guardian safety checks, gathers available research evidence, and generates a proposal tailored to the requested problem. The system is designed to support a broad range of tool concepts and implementation patterns rather than relying exclusively on a fixed catalogue of built-in tools.

Each successfully generated invention is stored in its own directory. Generated inventions remain proposals until they have been reviewed and approved by the repository owner.

**Default status:** `await_merge`  
**Execution policy:** proposal only  
**Automatic activation:** disabled  
**Approval authority:** repository owner

## How Inventions Are Generated

The intended generation workflow is:

1. **Demand received** — Genesis accepts a request describing a desired tool or capability.
2. **Guardian screening** — The demand is screened against the configured safety policy before research or generation proceeds.
3. **Research** — Available research collectors gather evidence and identify relevant references. Missing information must not be fabricated.
4. **Specification** — Genesis derives a structured specification covering the purpose, category, industry, capabilities, inputs, outputs, and safeguards.
5. **Capability planning** — Requirements, reusable-library candidates, implementation gaps, and review needs are documented.
6. **Artifact generation** — Genesis creates a proposal package containing the applicable generated source, tests, documentation, research evidence, and supporting plans.
7. **Review staging** — The proposal is stored with `await_merge` status for repository-owner review.

The actual artifacts produced depend on the invention type and the capabilities implemented by the current generator.

## Directory Organization

Each successful invention should occupy a distinct directory identified by its normalized resource name.

A typical proposal may include:

```text
inventions/
├── README.md
└── <invention-name>/
    ├── evidence.json
    ├── capability_plan.json
    ├── implementation_plan.json
    ├── acceptance_matrix.json
    ├── dependency_review.json
    ├── security_review.md
    ├── worldwide_context.json
    ├── code.go
    ├── library.go
    ├── openapi.yaml
    ├── hardware_guide.md
    ├── test.go
    ├── README.md
    ├── AWAIT_MERGE.md
    └── artifact_hashes.json
```

This is an illustrative artifact inventory, not a guarantee that every file exists in every proposal. Hardware-specific, library-specific, SDK, and review artifacts are generated according to the current forge implementation.

The root README describes the collection of inventions. Each invention's own README and metadata describe that individual proposal.

## Proposal Status and Approval

Every generated invention must remain distinguishable from a production-ready tool.

The `await_merge` status means that the proposal has been generated and is awaiting review. It does not imply that:

- The implementation has passed all tests.
- External research claims have been independently verified.
- Reusable-library candidates have been approved.
- The code is ready to deploy.
- Required legal, privacy, security, or hardware reviews are complete.
- The tool is available as an active production endpoint.

The repository owner must review the proposal and explicitly authorize any integration.

Approval to merge a proposal is not itself permission to bypass deployment, access-control, or production-release requirements.

## Safety and Execution Boundaries

Genesis-generated artifacts are untrusted until reviewed.

The invention directory must not be treated as an executable plugin directory. Merely placing source code or a library in this directory does not authorize the running engine to load or execute it.

Genesis must not automatically:

- Execute generated source code.
- Activate or deploy a proposed tool.
- Overwrite an existing invention without an explicit, reviewed process.
- Import unreviewed libraries into the running core.
- Install arbitrary dependencies.
- Weaken Guardian rules through generated content or external provider updates.
- Treat generated tests, research links, or metadata as proof of production readiness.

Where an invention requires hardware, its guide is a reference document rather than a wiring certification. Exact components, datasheets, electrical ratings, compatibility, and applicable safety requirements must be reviewed before implementation.

## Research and Evidence

Each proposal should preserve relevant research evidence and source provenance where supported by the generator.

Research must distinguish between retrieved records and reference links. Search links are leads for further investigation; they do not independently verify patent clearance, regulatory compliance, product prices, supplier stock, compatibility, or market demand.

Model-generated suggestions remain untrusted metadata and must not override deterministic safety requirements.

Unresolved assumptions and capability gaps should remain visible in the proposal rather than being silently presented as completed work.

## Testing and Acceptance

Before integration, the repository owner and designated reviewers should determine whether the proposal satisfies its acceptance criteria.

Where applicable, review should include:

- Source-code inspection and Go formatting.
- Unit and integration tests.
- Static analysis and security testing.
- Dependency and license review.
- Input validation and error-handling checks.
- API-contract compatibility.
- Privacy, consent, and access-control review.
- Hardware and electrical review where applicable.
- Integrity checks and artifact provenance.
- Rollback and operational-readiness planning.

A test file being generated is not evidence that the tests have passed. A successful build does not independently establish that the invention is secure or fit for production.

## Naming, Identity, and Persistence

Each invention should have a valid, normalized resource name that is suitable for its directory and API references.

Proposal creation should preserve existing invention records. If a proposal with the same identity already exists, the system should handle the conflict explicitly rather than silently replacing prior work.

Where revisions are required, preserve the relationship to the original proposal and record meaningful changes through a reviewed revision process.

Persisted evidence and capability plans should remain associated with the correct invention.

## Operating Principle

Genesis is designed to discover problems, propose tools, generate reviewable implementation artifacts, and support controlled expansion.

**Generate on demand. Preserve evidence. Keep proposals isolated. Review before merge. Test before integration. Approve before activation.**

This directory contains proposed inventions—not a collection of automatically trusted or running tools.
